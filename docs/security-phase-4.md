## ملخص التنفيذ

راجعت نتائج المرحلة الثالثة وأعدت اختبارات الانحدار والتدقيق المحلي. أُضيفت حزمة اختبارات عزل شركات لا تقبل إلا عنوان HTTP loopback، وتتحقق من قراءة/كتابة الأجهزة بين شركتين، أدوار المدير والمشغّل والمشاهد، محاولة التصعيد الذاتي، وعزل Storage. كما أضيف اختبار API غير موثق لا يقبل إلا Next.js محليًا.

تعذر تشغيل الاختبارات العملية لأن Docker وPostgreSQL وSupabase المحلي غير متاحين على الجهاز. أمر `supabase status --output json` فشل قبل أي اتصال بقاعدة بسبب غياب Docker daemon (`//./pipe/docker_engine`). لذلك لا تُعامل اختبارات العزل أو المصادقة أو Storage كناجحة؛ جميعها **Blocked**.

### مراجعة ثابتة

- `supabase-workspace.sql:20-40,98-102` يقيّد `workspace_records` بالشركة الحالية ودالة `workspace_write`، ويمنع trigger تغيير `organization_id` أو `module` بصورة غير مصرح بها.
- مسارات الخادم الحساسة تشتق الشركة من `get_my_access` بدل قبول معرف شركة من العميل: `pages/api/intake/admin.js` و`pages/api/platform/[section].js` و`pages/api/organization/users.js`.
- دوال `SECURITY DEFINER` في `supabase-multitenant.sql` و`supabase-workspace.sql` تضبط `search_path=public`، لكن تحقق الامتيازات الفعلي و`EXECUTE` يحتاج قاعدة محلية عاملة قبل اعتماده.

### سياسة `public.devices` القديمة

توجد مخاطرة ثابتة مؤكدة في منطق السياسة، لكنها **غير مثبتة تشغيليًا** دون التحقق من GRANT الفعلي:

- `supabase-multitenant.sql:200-201` يسمحان بـ INSERT/UPDATE عند `has_section_access('assets')`.
- دور Viewer يملك وصول قسم `assets` للقراءة وفق الدالة نفسها، بينما الكتابة الحديثة تستخدم `workspace_write('assets')`.

اقتراح التعديل محفوظ في `docs/security-phase3-legacy-rls-proposal.sql` ولم يطبق على أي قاعدة. اختبار Viewer في الحزمة الجديدة سيُثبت السلوك الحالي ثم يجب إعادة تشغيله بعد تطبيق الاقتراح على **قاعدة محلية فقط**. لا يوجد Migration إنتاجي جديد في هذه المرحلة.

## Storage والملاحظات

لم تنفذ اختبارات رفع أو تنزيل أو حذف Storage لأن خدمة التخزين المحلية لم تبدأ. الحزمة الجديدة تختبر قراءة ملف من مسار Organization B باستخدام Viewer A عند توفرها.

المخاطرة المفتوحة من المرحلة الثالثة لم تتغير: سياسة حذف `knowledge-files` قد تسمح لمالك المسار بحذف كائن مرتبط بملاحظة وترك سجل `knowledge_attachments` يشير إلى مسار غير موجود. هذه مشكلة اتساق داخل الشركة وليست إثباتًا لوصول عابر للشركات. يلزم اختبار محلي ثم اختيار حذف ذري عبر RPC خادمي أو سياسة تمنع حذف مسار مرتبط.

استمرت اختبارات XSS السابقة: اختبار Node يغطي HTML الغني والقديم، وPlaywright يتحقق في Chromium من بقاء التنسيقات المسموح بها وعدم تنفيذ markup غير موثوق.

### متطلبات استكمال التحقق قبل اختبار ما قبل الإنتاج

يلزم إتمام تثبيت Docker Desktop أو بديل متوافق، ثم تشغيل `pnpm run supabase:local:start` ومراجعة المخطط المحلي قبل أي reset أو seed. لأن المستودع يحتوي على ملفات تأسيس وMigrations تاريخية ولا يقدم سلسلة migrations مضمونة لإعادة بناء مخطط الإنتاج آليًا، يجب أولًا توثيق ترتيب تطبيق SQL في قاعدة محلية فارغة دون نقل بيانات. بعد ذلك تُشغّل `pnpm run test:tenant:local` مع مفاتيح `supabase status` المحلية فقط و`RUN_LOCAL_SUPABASE_TESTS=1`، ثم يعاد اختبار سياسة الأجهزة قبل اعتماد أي Migration.
