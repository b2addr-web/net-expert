## 1. عزل الشركات وRLS

المصفوفة التالية تستند إلى ملفات SQL ومسارات API الموجودة في المستودع، **ولا تثبت حالة السياسات المطبقة فعليًا**. تعتمد دالة `current_organization_id()` في `migrations/20261012_existing_account_workspaces.sql:10` على عضوية نشطة للمستخدم. تتطلب عمليات الكتابة في `workspace_records` دالة `workspace_write` وفق `supabase-workspace.sql:21,34-40,98`، وتتحقق واجهات الخادم من المستخدم برمز الجلسة عبر `getUser` ثم من الشركة عبر `get_my_access`.

**خطر محتمل متوسط:** سياسات `public.devices` القديمة في `supabase-multitenant.sql:200-201` تسمح بعمليات INSERT/UPDATE وفق `has_section_access('assets')`، وهو إذن قراءة القسم، بدل `workspace_write('assets')`. يتوقف الاستغلال على صلاحيات الجدول الفعلية وعلى بقاء هذا الجدول قابلًا للوصول؛ لم يُتحقق من ذلك بقاعدة معزولة. أُعدّ [اقتراح SQL](security-phase3-legacy-rls-proposal.sql) للمراجعة، **ولم يُنفذ**. قبل تطبيقه يجب اختبار مستخدم viewer وoperator ومسؤول في شركتين والتأكد من عدم كسر مسار قديم.

**خطر محتمل منخفض:** سياسة حذف كائنات `knowledge-files` في `migrations/20261021_knowledge_split.sql:168-172` تعتمد على مالك المسار، ولا تشترط عدم ارتباط الملف بملاحظة. قد يؤدي حذف كائن مرتبط مباشرة عبر Storage API إلى مرفق مكسور داخل شركة المستخدم نفسه. يحتاج تصميم سياسة/إجراء حذف ذري بعد اختبار التخزين المحلي؛ لا توجد إشارة إلى كشف ملف لشركة أخرى.

لم تُنفذ محاولات `SELECT/INSERT/UPDATE/DELETE` متبادلة بين شركتين أو طلبات API مباشرة بحسابات وهمية، لأن بيئة Supabase معزولة ومفاتيحها وحساباتها التجريبية غير متوفرة. المطلوب: نسخة محلية من المخطط مطابقة للإنتاج دون بيانات حقيقية، مستخدمان في شركتين ودوران بكل شركة، وفحص grants/RLS والدوال `SECURITY DEFINER` وسياسات Storage داخلها. لا يُنقل أي سجل إنتاجي إليها.

## 2. AES-GCM والروابط الخارجية

في `lib/intake-server.js:9-20`: مفتاح 32 بايت ناتج عن SHA-256 للسر الخادمي، وNonce من `randomBytes(12)`، ووسم بطول 16 بايت. أصبح فك الرمز يرفض الأجزاء المفقودة، الأحرف غير القانونية، الترميز غير القياسي، الأطوال الخاطئة والوسم/النص المعدّل برسالة عامة `INVALID_TOKEN`. بقي التنسيق `iv.tag.ciphertext` وBase64URL كما هو؛ اختبار التوافق مع رمز مُنشأ قبل الإصلاح نجح من حيث التنسيق وطول الحقول. اختبارات 64 Nonce منفصلة والتلاعب بالأجزاء الثلاثة والرمز الناقص ناجحة في `tests/intake-crypto.test.mjs`.

الروابط العامة **ليس لها انتهاء زمني مبرمج**؛ تعتمد على التعطيل اليدوي (`active=false`). لذلك اختبار انتهاء الصلاحية غير قابل للتنفيذ مع التصميم الحالي، ولم أضف انتهاءً قد يبطل روابط قائمة. تعرض واجهة الرابط العام نوع الرابط وعنوانه فقط، ويستمد إنشاء البلاغ/الطلب الشركة من الرابط المخزن، لا من جسم الطلب. `pages/api/intake/[token].js:43` يستخدم أول عنوان في `x-forwarded-for` لتحديد معدل الطلبات؛ فاعلية هذا الحد تعتمد على ضبط الوكيل الأمامي للهيدر، ولم تختبر على الاستضافة. لا يتيح الرابط العام تغيير الحالة.

## 3. HTML وXSS — نتائج Semgrep السبعة

أُعيد فحص قواعد `html-in-template-string` و`gcm-no-tag-length` المحلية: بقيت سبع إشارات HTML heuristic؛ اختفت إشارة GCM. التصنيف أدناه مبني على تتبع المصدر ومسار العرض واختبارات DOM/Chromium، لا على إسكات قاعدة الفحص.

## 5. تسجيل الدخول والتفويض

مراجعة ثابتة لـ `components/AuthContext.js`, `pages/auth/confirm.js`, `pages/reset-password.js` وواجهات API: الدخول يستخدم Supabase Auth، واستعادة الحساب `verifyOtp` لنوعي recovery/invite، وتغيير كلمة المرور يشترط `getUser` وصلاحية الاستعادة المؤقتة؛ الخروج يمسح ذاكرة الصفحة الرئيسية. API الإدارة يفحص رمز المستخدم مع `getUser` ويحدد الشركة من `get_my_access` قبل استخدام `service_role` أو RPC. لا توجد مفاتيح خدمة في `NEXT_PUBLIC_*` ضمن مسار الكود الذي فُحص.

لم تُنفّذ اختبارات دخول/خروج/تجديد/انتهاء جلسة أو تعديل صلاحيات عبر مستخدمين حقيقيين؛ اختبار Playwright السابق للصفحة المحلية واختبار XSS المعزول **ليسَا اختبار مصادقة**. يلزم مشروع Supabase اختبار وحسابات وهمية، وضبط redirect URLs للاختبار فقط، ثم اختبار الجلسات والروابط المحمية وطلبات API المباشرة وأخطاء التمييز بين الحسابات.

## الخطوة الرابعة المقترحة

1. توفير Supabase محلي/اختباري مجاني أو معزول بمخطط مطابق، بلا بيانات إنتاج؛ إنشاء شركتين وحسابات اختبار متعددة الأدوار، ثم تشغيل مصفوفة RLS/Storage/API واختبار اقتراح SQL القديم قبل أي تطبيق.
2. ترقية TipTap في فرع مستقل متكامل الحزم إلى إصدار مصحح، مع اختبار التنسيق والمرفقات والحفظ والفتح والنصوص العربية.
3. مراجعة مسار بناء CSS ونسخ Tailwind/PostCSS لتحديث محلل المحددات بصورة متوافقة، ثم إعادة التدقيق.
4. اختبار المصادقة والاستعادة وانتهاء الجلسة والروابط العامة في بيئة اختبار فقط، ومراجعة أثر `x-forwarded-for` عند وكيل النشر.

**حالة المرحلة:** أُنجزت الإصلاحات المحلية الموثقة واختباراتها، لكن تدقيق عزل الشركات الشامل لم يكتمل لعدم وجود بيئة اختبار Supabase. لا ينبغي اعتماد المرحلة على أنها إثبات نهائي لأمن الإنتاج.
